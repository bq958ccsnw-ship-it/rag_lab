# Учебная RAG лаборатория VirtHelp

Это небольшая офлайн-песочница для изучения retrieval и оценки качества RAG. Она повторяет основные идеи VirtHelp, но не требует Docker, VPN, RNGPT, токенов или доступа к боевому проекту.

В комплект входят 12 учебных документов, 30 размеченных dev-вопросов, 10 закрытых test-вопросов, детерминированный chunking, два локальных способа построения векторов, cosine similarity, retrieval-метрики и простой extractive answer. Все данные синтетические и созданы только для практики.

## Быстрый старт

Нужен Python 3.11 или новее. Устанавливать библиотеки не требуется.

```powershell
Set-Location rag_lab
python run.py retrieve "Сколько действует ссылка на исходный документ?" --top-k 5
python run.py answer "Когда блокируется неактивная учётная запись?"
python run.py evaluate --output results\baseline.json
python -m unittest discover -s tests -v
```

Baseline по умолчанию использует TF-IDF. Второй полностью локальный вариант запускается через `--backend hashing`.

```powershell
python run.py evaluate --backend hashing --output results\hashing.json
```

## Что происходит внутри

```text
Markdown документы
  → разбиение на фрагменты
  → TF-IDF или hashing-векторы
  → cosine similarity с вопросом
  → top-k фрагментов
  → document-level Precision@k, Recall@k, Hit@k и MRR
```

`TF-IDF` обучается только на корпусе документов. Вопросы лишь преобразуются уже обученным векторизатором. Так оценочные вопросы не влияют на словарь и IDF.

Размер фрагмента и overlap задаются в словах:

```powershell
python run.py evaluate --chunk-size 80 --overlap 0
python run.py evaluate --chunk-size 160 --overlap 30
```

В боевом VirtHelp целевой размер составляет 400 условных токенов, максимум 500 и overlap 40. В лаборатории значения меньше, потому что документы короткие.

## Данные и честная оценка

- `data/dev_questions.json` содержит вопросы, релевантные документы и ожидаемые факты. На dev можно анализировать ошибки и выбирать параметры.
- `data/test_questions.json` содержит только закрытые вопросы без ответов и меток.
- Test открывает и оценивает руководитель после того, как участник письменно зафиксировал финальную конфигурацию.

Нельзя подбирать `top_k`, chunk size, overlap или backend по test. Иначе test превращается в ещё одну dev-выборку и перестаёт измерять обобщение.

## Метрики

- `Hit@k`: найден ли хотя бы один релевантный документ в первых k результатах.
- `Recall@k`: какая доля всех релевантных документов найдена в первых k.
- `Precision@k`: какая доля первых k документов релевантна.
- `MRR`: обратный ранг первого релевантного документа, усреднённый по вопросам.

В отчёте нужно указывать конфигурацию вместе с метрикой. Число без chunk size, overlap, backend, `k` и версии набора вопросов невоспроизводимо.

## Структура

```text
documents/       учебный корпус
data/            открытые dev и закрытые test-вопросы
src/rag_lab/     chunking, vectorization, retrieval, evaluation
assignments/     задания каждому участнику
templates/       шаблоны эксперимента и анализа ошибок
instructor/      test gold, план этапа и вопросы на защиту
tests/           проверки лаборатории
results/         локальные результаты, кроме baseline в Git не добавляются
```

## Что сдаёт каждый участник

1. Исходный код изменений.
2. Команду полного воспроизведения результата.
3. Заполненный `templates/experiment_report.md`.
4. JSON или CSV с результатами всех прогонов.
5. Краткий разбор не менее пяти ошибок.
6. Финальную конфигурацию, зафиксированную до открытия test.

Отрицательный результат считается нормальным результатом. Например: overlap вырос с 0 до 20, Recall@5 не изменился, а число фрагментов выросло; гипотеза не подтвердилась.

AI можно использовать как помощника. На защите автор должен объяснить любой параметр, метрику и изменённый фрагмент кода. Непонятный автору код не считается выполненной работой.
